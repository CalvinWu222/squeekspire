## P0（bugs）

1. **选择型卡牌没有选择入口，实际行为与说明不符。**【代码确认；UI 可见卡面】Oracle Ping 承诺查看／调整未来三抽，Gud Tek 承诺升级一张手牌；`main.ts` 的 `playCard()` 仅提交 uid 和敌人 target，没有提交 choice，引擎只能默认第一个候选。第一局实际使用了 Gud Tek，但没有出现选牌过程。建议加入预览与目标选择，确认后才消费瓜子；取消不消耗。验收：选择第二个候选后，回放及抽牌／升级结果与所选一致。位置：`src/main.ts` 的 playCard、`src/game/engine.ts` 的 oracle-ping／gud-tek 分支。

2. **Exit Liquidity 在 FUD 下打出不能转移 FUD。**【独立代码夹具确认，未宣称 UI 随机抽到】通用首牌逻辑先清除 `c.fud`，再进入此卡分支，导致已经找不到待转移状态；附加 Weak 后也没有刷新缓存的敌人意图。夹具中 FUD 下先打此卡，敌人 Weak 仍为 0，仍造成原本 6 点伤害。建议先确定并转移状态，再执行通用首牌消耗，统一刷新意图，并明确定义敌人 FUD 的效果。验收覆盖 FUD／Weak、首牌／非首牌及预告伤害。位置：`src/game/engine.ts` 的 play、exit-liquidity、tail-whip。

3. **部分卡牌可以花掉休息升级机会，却没有实际升级收益。**【代码确认】休息列表只筛 `level===0`；ser、Insomnia、Genesis Seed 等没有读取等级的有效升级分支，仍会变成“+”并显示“Upgraded values active”。建议给每张可升级牌定义明确升级效果，并在休息处展示前后对比；尚无效果的牌暂不提供升级。验收：所有可选牌升级前后至少一项规则有效变化，不能只改变名称。位置：`src/main.ts` 的 rest／cardMarkup，`src/game/engine.ts` 的升级与对应效果分支。

4. **Touch Grass 已用过后仍呈现为可打出的零费卡。**【第一局 UI 复现】最终 Boss 首回合、0 瓜子时该卡仍亮着且可点击，才弹出“Touch Grass is once per run”；见对应截图。建议在用过后禁用此牌并在卡面直接说明原因，或按明确规则从本局牌组移除。验收：下一场再抽到时可用状态、提示、点击结果一致，玩家不必试错。位置：`src/main.ts` 的 cardMarkup、`src/game/engine.ts` 的 touchGrassUsed 检查。

## P1（UX/clarity）

1. **卡面应显示当前有效数值。**【UI＋代码】升级后的 3AM Dash、Wheel Kick 等仍以原始说明开头，另附“升级生效”；其他升级／合并牌连有效结果都无法从卡面确定。例如升级 Sunflower Stash 实际 8 Block，仍写 5。建议卡面、无障碍说明、升级预览共用有效数值计算，区分基础值与结果。验收：玩家仅看卡面即可预测本次伤害／格挡，无需查引擎。位置：`cardMarkup()`、`cardAmount()`。

2. **手机手牌说明过小，横向找牌后仍难读。**【390×844 UI】当前手牌正文约 6.5px，费用／卡名可辨，但整句规则及升级说明难读。建议点击非出牌区可打开清晰的大卡预览，正文至少采用适合移动阅读的字号，并保留明确的出牌／取消操作；避免预览时误打出技能。验收：手机无需浏览器放大即可读完整规则和比较卡牌。证据：best2 截图；位置：`src/style.css` 的移动手牌规则。

3. **敌人意图应反映已经施加的减伤。**【代码确认】Fluff Up 把临时减伤存在 powers，结算才扣，头顶攻击值不变化。建议意图显示预计实际伤害，或明确标出“本回合每段 −2”，多段攻击也保持一致。验收：预告、Block 消耗和实际 HP 损失相符。位置：`src/game/engine.ts` 的 fluff-up／endTurn，`src/main.ts` 的敌人意图。

4. **休息和事件选择要展示实际收益，避免原始数字误导。**【第三局 UI＋代码】71/72 HP 时事件仍写 Heal 10；休息固定写 Heal 22；“greeting card”不说明候选池。低血事件写失去 6 HP，但引擎最低保留 1。建议在按钮旁展示选择后的 HP／金币与可能卡牌，满血治疗标明实际 +0。验收：预览数值与点击后的顶栏一致。证据：best4、run1_rest；位置：rest／event 及对应 reducer 分支。

5. **遗物与合并目标缺少可辨认的预览。**【UI＋代码】顶栏所有遗物都是同一月亮图案，积累后无法快速判断被动；Merge 则暗中选择牌库第一组副本。建议遗物提供差异图标和可点击说明；Merge 显示将消失的两张牌及产物，让玩家确认目标。验收：手机也能查遗物，且不查内部牌序便能预测合并结果。位置：header、merge 分支。

## P2（balance/fun）

1. **优先调整前期连续精英、后期连续补给的节奏。**【三局 UI＋地图代码】第一局连续打 Hour 05–08 的同型 Oracle Judge，HP 从 72 降到 43；后段则多次连续商店／休息。第二局捷径只打三场精英即可通关；第三局到事件前也需三场 Oracle Judge。建议对连续同型精英设上限，给同幕分支安排“风险换奖励／补给保命”的实质选择，同时保留工作量映射。验收指标：连续重复房间数、新手到第一幕关卡的存活率、分支选择分布。位置：`src/game/map.ts` 的 tier／kind 规则。

2. **Buildooooor 的效率需要单独评估。**【代码确认；第一局购买并使用】它 1 瓜子初始 20 伤害，每次再 +5 且跨战斗成长；对照 Wheel Kick 1 费 6、Burst Sprint 1 费 9、Wood Chew 2 费 14，普通攻击之间差距很大。建议先统计选取率、单位费用有效伤害与成长后通关率，再决定初值／成长频率或为其他攻击增加差异化收益。本轮仅三局，不能据此断言唯一最优构筑。位置：catalog 与 buildooooor 伤害计算。

3. **结算应解释分数来源，并让重复练习有进步目标。**【UI 数据】第二局只有 6 场战斗、最大单击 54，却得到 7,894 分；第一局 9 场、最大单击 102，只有 1,170 分。构筑／倍率不同足以造成差异，但结算只列总分与最大单击，玩家很难知道哪里做得更好。建议列出基础 Squeeks、关键倍率／连击、逐战得分和承伤；同日重开标明固定路线，并比较上局回合数与承伤。验收：玩家能从结算解释主要分差，再据此设定下一次练习目标；不要仅凭这三局判断分数存在漏洞。位置：result、scoreBattle、effectiveMult。

4. **开场补给房的自动跳过需要明确反馈。**【代码＋三局回放】Start 会把首战前 shop／rest／event 全部自动 leave；当前日开场三房虽在回放中“访问”，玩家从未选择，75 初始金币要经过精英后才可用。建议保留快速开战的意图，同时给一个可选开局补给，或在地图清楚标识“开场略过”，避免误以为已使用过这些房间。验收：新玩家能够解释为何从 Hour 04 开始及起始资源如何使用。位置：startRun。

## 复现入口

本机 PATH 已配置 portable Node。先运行 `npm.cmd run dev`，再以实际服务地址运行：

```powershell
$env:SQUEEKSPIRE_URL='http://127.0.0.1:5174/'
node .tmp/shots.mjs --playtest
node .tmp/analyze-playtest.mjs
```

`.tmp` 是本地临时工具目录；源码审阅的独立证据脚本为 `.tmp/review-engine.mjs`。本轮没有推送、部署、打开 Discord 或操作钱包。
